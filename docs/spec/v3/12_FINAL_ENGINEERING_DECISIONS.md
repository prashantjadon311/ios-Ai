# V3 Frozen engineering decisions, architecture and release lines
## Product boundary
Build one *actual usable* native iOS/iPadOS SwiftUI app in one integrated campaign, using strict compile/test sub-gates. Five primary destinations: Dashboard, Tasks, History, Configuration, Settings; Chat and Approvals are routed surfaces. Two independently editable avatar identities Maya and Saar. Use a shared assistant engine and per-identity voice/style/provider overrides. A profile switch is not an authenticated account switch.

## Delivery lines (must not be blended)
**V1 required:** text chat; local-first SwiftData conversations, tasks, history and explicitly saved memories; usable Dashboard and both assistants; BYOK Groq/OpenRouter plus strict custom-compatible adapter; streamed responses with honest interruption handling; tap-to-talk on supported Speech locale and native TTS; task create/edit/cancel and local reminders; simple typed tools and approval screen; secure credential storage; privacy modes; diagnostics; responsive iPad/iPhone navigation; localized permissions and app UI basics.
**V1 conditional, compile+runtime-gated:** Apple Foundation Models; newer speech pipeline; Vision OCR; Core Spotlight; Calendar/Contacts integrations; continued background processing. Conditional features must not be the only implementation of a required workflow.
**Contract only, not V1 UI promises:** Small AI serving, secure managed provider gateway, remote autonomous scheduler, Sign in with Apple + Firestore per-user sync + encrypted Google Drive backups, Siri extensions, widgets/Live Activities. No CloudKit/iCloud. Cross-device user separation remains future cloud work, not an accomplished V1 feature.

## Platform and tooling boundary
- Generate a blank `.swiftpm` using actual iPad Swift Playgrounds. Record raw exported project tree and app settings. Preserve its app manifest generated by Playgrounds. Place the portable Swift source into its verified app target. Never invent an app-manifest syntax from the logical tree.
- If a Mac/Xcode exists, compile an Xcode wrapper sharing those sources with Swift 6 complete-concurrency checking. Xcode Cloud needs an Xcode project wrapper; an exported standalone Playground cannot be assumed directly supported.
- If only Windows/Linux VS Code is available, syntax/static fixture tests are possible but iOS-framework compilation and physical-device validation remain NOT_RUN. Do not try to manufacture xcodebuild output.
- iPhone installation is a separate supported signing/distribution problem; coding in iPad Playgrounds is not the same as installing directly on iPhone.
- Deployment floor iOS/iPadOS 18 is a *proposed* target, validated at W00. Availability-gate all newer APIs and do not import unavailable symbols into files that are compiled for old SDKs without compile checks.

## Source ownership diagram
SwiftUI @MainActor -> ApplicationCommandBus / AppSession -> AssistantOrchestrator actor -> ContextBuilder + PrivacyPolicy -> IntelligenceRouter -> one verified AssistantModel provider -> stream normalizer -> persisted messages -> MainActor UI. Tool proposals go through ToolRegistry -> Policy -> Approval -> DurableToolLedger -> exact executor -> redacted audit. All sensitive storage passes a storage actor, immutable domain mapping and explicit owner. Local notifications schedule *alerts*, not AI execution. Voice has exactly one session owner and one capture state machine. Assets have independent resource loader.

## Dependency rules
- Domain cannot import SwiftUI, networking, SwiftData, cloud SDKs, UIKit or provider-specific wire DTOs.
- Presentation imports application protocols and domain DTOs, not concrete repositories or URLSession transports.
- Persistence alone imports SwiftData; map @Model objects to immutable Sendable domain records inside its isolation boundary.
- AI provider adapters know wire formats, not UI; no provider makes device tool calls.
- Tool executors cannot invoke the AI router; only the orchestrator may request model continuation.
- Only CompositionRoot constructs concrete services. Models and renderer classes are not singletons.
- Conditional/future targets are isolated behind protocols and are excluded from V1 app target when unavailable.

## Explicit defaults
- App remains usable without an account and without an AI key for local tasks, settings and history. Show first-run provider setup; no secret included in bundle.
- Provider model catalog is runtime-discovered or user-configured and capability-tested; no claim a given free model ID or price will remain available.
- Unknown route capability, confidentiality guarantee, token context, destination or side-effect idempotency fails closed for the relevant operation.
- User-initiated tap-to-talk only; no always-listening/microphone background service. Cloud STT needs separate opt-in.
- Direct BYOK budget controls are *advisory* and require clear labeling; hard spending guarantees require server/provider restrictions.

## Stable business entities
OwnerProfile, AssistantProfile, Conversation, Message, Attachment, MemoryItem, TaskDefinition, TaskRun, TaskStep, ToolProposal, Approval, ToolReceipt, AuditEvent, ProviderConfig, ModelDescriptor, UsageEstimate, AppPreference. Use UUID identity + owner on every private object; task definitions and mutable settings have monotonically increasing revision; secrets are Keychain references only. Fields and state transitions are frozen in V2 `02_CANONICAL_CONTRACTS.md`, except V3's stricter tool, fallback and account boundaries.

## Implementation risks not solvable by prose
No actual iPad template, no macOS/iOS SDK compiler in this environment, no real API credentials, no device locale/Apple Intelligence evidence, no valid signing profile. All of these are external acceptance gates for Sonnet, not reasons to invent success. Record precise blocker and continue independent pure Swift/UI/code work.
